# 知识库自动维护

配合 `local-kb` 这组 MCP 工具使用。核心不是"多写"，而是**该写的写、该改的改、不该写的不写**。

## 一、动笔前：先读，别凭记忆

1. 用 `search_knowledge_base` 查与任务相关的**规范 / 模板 / 约定 / 历史决策**（关键词用业务名词，不要用"文档""规范"这类空词）。
2. 命中就按库里的来，冲突时以库里更新的为准，并在回复里说明"依据《…》"。
3. 库里什么都没有，再按通用最佳实践写，并在产出末尾注明这是新约定。
4. 需要成段理解背景时用 `ask_knowledge_base`，只要原文片段时用 `search_knowledge_base`。

## 二、收工后：自己判断要不要入库

同时满足才写，缺一条就跳过：

- **会复用**：下次遇到同类任务还会再看（规则、模板、结论、口径、踩坑）。
- **非即时**：不是这次对话的中间态、草稿、TODO。
- **非原文可查**：不是代码、配置、原始文档里已经写清楚的东西。
- **有归属**：能说清它属于哪个主题、以后用什么关键词能找到。
- **不含敏感信息**：密钥、令牌、个人隐私一律不入库。

拿不准就问用户一句"这条要存进知识库吗"，别自作主张灌进去。

## 三、写入方式：选对工具

| 情况 | 用什么 | 结果 |
| --- | --- | --- |
| 写完/改完一个文件（方案、规范、报告） | `sync_document(file_path, tags=[...])` | 同路径覆盖旧版本，内容没变自动跳过 |
| 只有一段结论 / 规则 / 模板 | `save_note(title, text, tags=[...])` | 落地为 notes/*.md，同标题覆盖 |
| 网页资料 | `add_web_page(url)` | 抓正文入库 |
| 只想知道库里有什么 | `list_documents` / `kb_status` | 只读，不写 |

## 四、去重：改旧的不建新的

- 写之前先 `search_knowledge_base` 或 `list_documents`，确认是否已有同主题文档。
- 已有：**改原文件再 `sync_document`**，不要换个名字另存一份。
- 标题稳定：用「前端代码规范」而不是「前端代码规范-2026-10-23」；日期和版本写进正文。
- 同一主题只维护一份，碎片结论用 `save_note` 归到稳定标题下。

## 五、留痕：记录用了什么

当产出依赖模型或既有规则时，在文末或笔记末尾加一行：

```
生成信息：模型 <model>；依据《文档A》《文档B》；更新于 YYYY-MM-DD
```

这样以后回看能知道结论是怎么来的，也能判断是否需要重跑。

## 六、失败处理

- 工具报"连接不上知识库服务"：提示用户 `cd /home/chen/Project/zhiku && ./start.sh`，或确认 `RAG_BASE_URL`。
- 报"请先配置向量模型接口"：让用户到 WebUI「设置」里填向量接口，不要自己编造。
- 入库后状态是 `error`：读 `list_documents` 里的错误原因，通常是扫描件 PDF 或向量接口不可用。

## 七、别做的事

- 不要把整段对话记录、调试日志、临时脚本塞进知识库。
- 不要为了"显得勤快"每次都写；没有新增信息就不写。
- 不要用 `add_document` 反复上传同一份文件（会产生重复文档），用 `sync_document`。
